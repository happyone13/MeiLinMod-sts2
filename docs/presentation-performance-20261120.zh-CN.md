# 梅铃、友纪：0.113.1 表现层与发布包

本轮不改变 Spine 的渲染方式，不降低卡面分辨率或动画帧率。体积是对本机新旧 PCK 的实测；没有测量实战帧耗时，不从包体推断 FPS 或内存收益。

| Mod | 旧 PCK | 新 PCK | 变化 |
| --- | ---: | ---: | ---: |
| MeiLinMod | 323.20 MiB | 178.64 MiB | -144.56 MiB（44.73%） |
| YukiMod | 366.17 MiB | 157.37 MiB | -208.79 MiB（57.02%） |

## 本轮边界

- 卡框只接管本角色的卡。按实际创建的节点回收覆盖层，对模型引用而不只是卡牌类型做判定；换模型时在原版重画前交还旧状态。不要对未接管节点执行“恢复原版默认值”，其他 Mod 可能刚写过这些值。
- 梅铃普通攻击的特效在当前命令节点下播放，保证变换、绘制顺序和命令中断语义；已完成的实例回到本房间。并发播放使用不同实例，回收有代次检查，每个键最多保留两个空闲实例。
- UX 仅为对应参战角色的已开启演出预取前三帧；播放按时间推进四帧窗口，离场或关闭功能时释放引用。房间预取和播放共用同一 Mod 的加载请求上限。极冷启动时仅为第一张图在演出开始前异步等待，预算 100 ms（低帧率下返回可晚一个调度帧）；图已就绪不多等一帧，失败或超时也不阻断结算。UG 和卡牌伤害逻辑不变。
- 友纪的十个 Gloomy 特效作为其遭遇的额外资源，由原版战斗房间加载/释放；不是在 Mod 启动时永久持有。非友纪提供的遭遇不申请这些路径。原版 0.113.1 的开战与读档恢复入口都会取选中的遭遇资源，提供方优先级不变。
- 两个项目保留全部源 JSON；只把确认有 Spine 二进制导入对应物、无直接运行时引用的 137 / 80 个骨骼源文件排除在 PCK 外。没有排除整类 JSON，时间轴、本地化、VFX 命令和未配对资源不受影响。

每个仓库的 `tools/spine_export_sources.py` 都能维护和核查自己的白名单。新增或切换骨骼格式时，在对应仓库运行：

```powershell
python tools/spine_export_sources.py --mod MeiLinMod --update
python tools/spine_export_sources.py --mod MeiLinMod --pack <新PCK> --baseline <旧PCK>
```

友纪将 `--mod` 改为 `YukiMod`。对照检查包括旧包中该 Mod 资源和 `.godot/imported` 下的运行时资源路径，以及每个 `.skel.import` 指向的二进制；不是只比较文件数量。如果新增代码会**拼接** JSON 路径，应显式检查该路径，不能期待引用扫描推断出任意拼接逻辑。对新包所有 `.ctex` 的原始字节做 SHA-256 分组，同一 Mod 内完全相同的额外副本只有梅铃 6.01 MiB、友纪 5.48 MiB；这是磁盘体积上限，不是显存测量。

## 本机验证

- 游戏 v0.113.1、RitsuLib 0.6.15；两个项目及其测试均编译通过，0 警告、0 错误。未部署到 Steam 正式目录。
- 共 24 个针对性游戏内测试通过：双 Mod 卡框 5 个、旧版放大卡框约定 1 个、梅铃房间特效池 2 个、友纪 Gloomy 8 个、两边 UX 帧窗口 6 个、UG/UX 完整图形回归各 1 个。测试日志和产物在本工程 `tmp/performance-build/`。
- 卡框分别以两种 Mod 加载顺序运行。在真实 `NCard` 上做“梅铃 → 友纪 → 梅铃 → 原版打击”，与同画面新建的原版打击比较：194,572 个有效像素（两图任一 8 位 alpha ≥ 21）的 RGBA 全部相同。截图为 `tmp/card-frame-coload-vanilla.png`。此结论限于这条复用链，不代表和所有第三方卡框都做过实测。
- Gloomy 验证了遭遇资源枚举、十个可实例化场景、提供方、存档状态、双人逃离及奖励。演出验证了真实首帧、取消/超时、命中时钟、画面与模型恢复；不是人工完整跑了一局，也没有对比 P95/P99 帧耗时。

## 下一轮优先级

1. **梅铃姿态光环。** 保持同一姿态不会重建光环，但两个持续发射器分别按 0.05/0.04 秒创建一个短命 `Sprite2D`，即约 1,200/1,500 个每分钟（不含入场爆发，不等于同时在场数量）。`MeiLinStanceVfxController.ClearAura` 现只让子节点收尾，无脚本的旧根留到模型销毁。先回收已播完的根，再在发射器内复用精灵；验证保持一分钟与连续切换 20 次后的节点数、长帧和尾效完整性。
2. **两边可见的动态卡面。** 屏外/被裁剪时已有停更，优先消除布局未变时重复的尺寸、锚点、渲染模式写入，保留可见性变化和移动时的裁剪检测。不必先给可见卡面限帧。用同一手牌在静止、滑动和放大预览三个状态对比主线程与渲染耗时。
3. **演出中多目标的共用轨迹。** `ug_stage.gd` 的 `apply_motion()` 对每个敌人用同一个时间采样同一条轨迹，`track_pose()` 每次都建字典并遍历骨骼。可以每帧只算一次公共敌方姿态，再分别应用敌人的初始变换、偏移和层级。先对比单目标与四目标演出的脚本帧耗时和同一时间点的位置，再决定是否值得优化曲线采样。
